# Automatic Batching

Batching означава "събиране на няколко обновления на състоянието в един рендер". React винаги е правил това вътре в своите event handler-и. От React 18 го прави навсякъде: в `setTimeout`, в `Promise.then`, след `await`, в native event listener-и. Това намалява броя рендери и премахва цял клас бъгове с междинни състояния.

## Аналогия: пазаруване с един курс

Ако майка ти каже "купи хляб" и две секунди по-късно "купи мляко", можеш да отидеш два пъти до магазина или да изчакаш секунда и да отидеш веднъж с двете неща. Batching е второто: React изчаква, докато свърши текущата работа (handler-ът, callback-ът), събира всички `setState` и прави един рендер с крайните стойности.

## Демо: преброй рендерите

Режимът "React 17" е емулация: всяко `setState` извън event handler е увито във `flushSync`, което е точно поведението на стария legacy режим, в който React нямаше как да знае кога свършва един `setTimeout` callback и прилагаше всяко обновление веднага.

## Какво точно се случва

```jsx
function handleClick() {
  setA(a + 1);   // React слага обновлението в опашка, не рендерира
  setB(b + 1);   // още едно в опашката
}                // handler-ът свърши: React рендерира веднъж с a+1 и b+1
```

Механизмът: всяко `setState` добавя обновление в опашката на съответния hook (`queue.pending`, виж [Свързан списък](Linked_List.md)) и маркира fiber-а и пътя до корена с lane (приоритет). Самият рендер се планира чрез scheduler-а като отделна задача. Докато текущият синхронен код тече, задачата не може да започне, затова всички обновления, направени в същия тик, се събират. В React 17 това работеше само защото React изрично "отваряше" batching преди да извика твоя handler и го "затваряше" след това. Извън handler-а нямаше кой да затвори, затова всяко `setState` рендерираше веднага.

В React 18 с `createRoot` рендерът винаги се планира по приоритет (lane), не по "дали сме в handler". Две обновления с един и същ приоритет в един и същ тик попадат в един рендер, независимо откъде са извикани. Затова се нарича automatic.

## Какво вижда потребителят без batching

Ако `setA` и `setB` предизвикат отделни рендери, за кратък момент компонентът е рендериран с `a` ново и `b` старо. Обикновено това е само загубена работа, но понякога е бъг: условие като `if (a > 0 && b === 0) showError()` се задейства, въпреки че "логически" двете стойности се променят заедно. С batching такова междинно състояние не съществува.

## Кога не искаш batching: flushSync

Понякога ти трябва DOM-ът да е обновен веднага, например за да измериш размер или да скролираш до нов елемент:

```jsx
import { flushSync } from 'react-dom';

function addMessage(msg) {
  flushSync(() => {
    setMessages((m) => [...m, msg]);   // рендерира и обновява DOM веднага
  });
  listRef.current.lastChild.scrollIntoView();  // новият елемент вече е в DOM
}
```

`flushSync` принуждава React да рендерира синхронно, преди да продължи. Използвай го рядко: всяко извикване е отделен рендер и блокира до commit.

## Функционална форма на setState

Batching е и причината да ползваш функция в `setState`, когато новото състояние зависи от старото:

```jsx
setCount(count + 1);          // двете четат същото count от затварянето
setCount(count + 1);          // резултат: +1, не +2

setCount((c) => c + 1);       // React прилага функциите една след друга
setCount((c) => c + 1);       // резултат: +2
```

При batching React пази опашката от обновления и ги изпълнява при рендера. Функционалната форма получава резултата от предишното обновление, затова работи правилно и при няколко извиквания.

## Капани

- `createRoot` е задължително. С `ReactDOM.render` (legacy API) React 18 пази старото поведение.
- `flushSync` вътре в lifecycle метод или ефект работи, но вътре в render е грешка.
- Обновления с различен приоритет не се събират: `setState` в handler (sync lane) и `startTransition(() => setState())` (transition lane) са два рендера по дизайн. Виж [useTransition](useTransition.md).
