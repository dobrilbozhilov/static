# Кога се пререндерира един компонент

Рендер означава "React извиква функцията на компонента, за да разбере какво трябва да има на екрана". Това не е същото като промяна на DOM. Компонент се рендерира по точно четири причини: негов `setState`, рендер на родителя му, промяна на context, за който е абониран, или сигнал от външен store през `useSyncExternalStore`. "Промяна на props" не е в списъка, защото props се променят само когато родителят се рендерира.

## Аналогия: вълна по стълбите

Представи си сграда с етажи и на всеки етаж по няколко стаи. Ако някой на третия етаж извика "промяна!", всички стаи под него на четвъртия, петия и т.н. го чуват и се проверяват. Стаите над него не чуват нищо. Вратата с табела "memo" спира вълната: зад нея проверяват само ако някой е променил нещо на самата табела (props). Единственото изключение е високоговорителят (context): той се чува във всяка стая, която го е включила, дори зад затворена memo врата.

## Четирите причини

| Причина | Какво се рендерира | Пример |
|---|---|---|
| `setState` / `dispatch` в компонента | компонентът и цялото му поддърво | `setCount(c + 1)` |
| Родителят се рендерира | всички деца, освен ако има bailout | каквато и да е причина по-нагоре |
| Context Provider получава нова стойност | всички consumer-и на този context и техните поддървета | `<ThemeContext.Provider value={theme}>` |
| `useSyncExternalStore` получава нов snapshot | компонентът, който го ползва | Redux, Zustand, `window.matchMedia` |

Класовите компоненти добавят `forceUpdate`, а `key` смяната е не рендер, а unmount + mount.

Важно: вълната върви само надолу. Рендер на `Item 2` никога не рендерира `List` или `App`. Това е причината "state надолу, колкото се може по-близо до мястото, където се ползва" да е най-ефективната оптимизация: малък setState, малка вълна.

## Рендер не е равно на DOM промяна

След рендера идва reconciliation ([Render Phase](Render_Phase.md)): React сравнява новия резултат със стария и отбелязва само реалните разлики. Компонент може да се рендерира сто пъти и да не докосне DOM нито веднъж, ако връща същото. Затова "излишен рендер" обикновено струва само време на JavaScript, не на браузъра. Това е и причината да не оптимизираш, докато не си измерил: виж [Профилиране](Profiling.md).

## Bailout: кога React прескача

В `beginWork` React проверява три условия, преди да извика компонента:

```js
if (
  oldProps === newProps &&          // същата референция на props обекта
  !hasContextChanged() &&           // няма нов context за този fiber
  !includesSomeLane(fiber.lanes, renderLanes)   // няма чакащ setState в него
) {
  return bailoutOnAlreadyFinishedWork(...);     // прескочи целия възел и поддървото
}
```

Първото условие обяснява почти всичко. Когато родителят се рендерира, той изпълнява своя JSX, което създава нов обект props за всяко дете: `<Child a={1} />` всеки път е нов `{ a: 1 }`. Референцията е различна, bailout няма, детето се рендерира, дори стойностите да са еднакви. Има два начина референцията да остане същата:

1. Елементът идва отвън като `children` или друг prop. Родителят не го създава, просто го подава нататък.
2. `React.memo`: React сравнява props по стойност (плитко) и ако са равни, прави bailout въпреки новата референция.

## Трикът с children

```jsx
function App() {
  return (
    <Scroller>              {/* Scroller държи state за scroll позицията */}
      <HeavyTable />        {/* създаден тук, в App */}
    </Scroller>
  );
}

function Scroller({ children }) {
  const [y, setY] = useState(0);
  return <div onScroll={(e) => setY(e.target.scrollTop)}>{children}</div>;
}
```

При всеки `setY` Scroller се рендерира, но `HeavyTable` не: елементът `<HeavyTable />` е създаден в App, App не се е рендерирал, значи `children` е същият обект и `beginWork` прави bailout. Без memo, без useMemo. Това се нарича "lift content up" или "move state down" и е първото нещо, което да пробваш преди `React.memo`. В демото горе това е Footer: подаден от App на Content.

## React.memo като граница

`React.memo` обвива компонента с плитко сравнение на props. Ако всички props са `Object.is` равни на предишните, React прави bailout на компонента и на цялото поддърво под него. Границата държи, стига props наистина да са равни: inline обект, масив или функция я чупи на всеки рендер. Подробно: [React.memo](React_memo.md).

Context минава през memo. Промяна на Provider стойността маркира всеки consumer fiber директно (React обхожда поддървото и търси абонирани fiber-и), затова consumer-ите се рендерират, дори всичко над тях да е прескочено.

## setState със същата стойност

```jsx
setCount(5);   // count вече е 5
```

React сравнява с `Object.is` и ако стойността е същата, не планира рендер. Има един нюанс: в някои случаи React все пак извиква компонента още веднъж (eager state проверката е оптимизация, не гаранция), но не продължава надолу към децата и не commit-ва нищо. Ако видиш един допълнителен рендер на самия компонент при равна стойност, това е нормално.

За обекти "същата стойност" означава същата референция: `setUser({ ...user })` винаги рендерира, дори съдържанието да е еднакво.

## Капани

- Контекст с обект като стойност: `<Ctx.Provider value={{ user, setUser }}>` създава нов обект при всеки рендер на Provider компонента и всички consumer-и се рендерират. Стабилизирай с `useMemo` или раздели на два context-а.
- Inline компоненти: ако дефинираш компонент вътре в друг компонент, при всеки рендер типът е нова функция и React прави unmount + mount, не рендер.
- Рендерът е евтин, докато не стане скъп. Не слагай memo навсякъде превантивно: виж [useMemo и useCallback](useMemo_useCallback.md).
- Custom hook, който ползва `useState`, предизвиква рендер в компонента, който го ползва, не "в hook-а".
