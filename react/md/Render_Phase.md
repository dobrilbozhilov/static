# Render Phase

Render фазата е първата половина от работата на React по едно обновление: от момента, в който има чакащо `setState`, до момента, в който е готово ново дърво с отбелязани промени. В нея React извиква компонентите ти, сравнява резултата със старото дърво и записва върху всеки fiber какво трябва да се направи. Не докосва DOM. Затова може да бъде прекъсната, изхвърлена и започната отначало, без потребителят да види нещо.

## Аналогия: чернова на писмо

Когато пишеш писмо на чернова, можеш да зачеркваш, да спираш, да го оставиш за утре. Никой не вижда черновата. Чак когато преписваш на чисто, е важно да не те прекъсват. Render фазата е черновата: React изчислява и отбелязва, а [Commit Phase](Commit_Phase.md) е преписването на чисто.

## Какво прави beginWork

За всеки fiber, който стига до него (виж [Свързан списък](Linked_List.md) за реда), `beginWork` решава дали изобщо има работа и ако има, я върши:

1. Проверява за bailout. Ако `pendingProps === memoizedProps`, компонентът няма чакащи обновления (неговите `lanes` са празни) и context-ът не е променен, React прескача компонента изцяло и само проверява децата му по `childLanes`. Това е причината `React.memo` и стабилните props да помагат: те правят условието вярно.
2. Извиква компонента. За функционален компонент това е `renderWithHooks`: вика функцията ти, обработва опашките на `useState`, събира ефектите.
3. Reconcile на децата. Резултатът от компонента (JSX, тоест обикновени обекти `{ type, props, key }`) се сравнява с текущите деца на fiber-а. За всяко дете React или преизползва стария fiber, или създава нов, и записва флаг.
4. Връща първото дете като следваща единица работа.

```js
// Опростен beginWork
function beginWork(current, workInProgress) {
  if (current !== null && !hasPendingWork(workInProgress)) {
    return bailout(current, workInProgress);   // клонира децата, не вика компонента
  }
  const children = renderWithHooks(workInProgress);      // извиква твоята функция
  reconcileChildren(current, workInProgress, children);  // diff + флагове
  return workInProgress.child;
}
```

## Какво прави completeWork

`completeWork` се вика, когато всички деца на един fiber са готови. Качва се нагоре и върши работата, за която трябва да знае какво има под него:

- За DOM елемент (HostComponent) при първо рендериране създава истинския DOM възел с `document.createElement` и прикачва към него вече готовите DOM възли на децата. Възелът още не е в документа: целият поддърво се сглобява "в ръката" и се вмъква наведнъж в commit фазата.
- При обновяване сравнява старите и новите props на елемента и подготвя списък с промените (`updatePayload`): кои атрибути, стилове и event handler-и са различни. Ако има разлики, маркира fiber-а с `Update`.
- Събира флаговете на децата в `subtreeFlags`. Така в commit фазата React знае, без да обхожда цели поддървета, дали вътре има нещо за правене. В по-старите версии това беше свързан списък от ефекти (effect list), днес е битова маска плюс обхождане само на маркираните клони.

## Флаговете

Всеки fiber носи `flags`: битова маска, която commit фазата чете. Най-важните:

| Флаг | Кога се вдига | Какво прави commit фазата |
|---|---|---|
| `Placement` | Нов fiber или преместен в списъка от братя | Вмъква DOM възела на правилното място |
| `Update` | Променени props на DOM елемент, или ефект за изпълнение | Прилага `updatePayload`, пуска layout ефекти |
| `ChildDeletion` | Родител, чието дете е изчезнало | Изтрива DOM поддървото от `deletions` на родителя |
| `Passive` | Компонент с `useEffect`, чиито зависимости са променени | Планира ефекта след paint |
| `Ref` | `ref` е сложен или сменен | Откача стария, прикачва новия ref |
| `Snapshot` | Клас с `getSnapshotBeforeUpdate` | Извиква го преди mutation |

Изтритите fiber-и не са в новото дърво, затова не могат да носят флаг. Вместо това родителят получава `ChildDeletion` и списък `deletions`.

## Диф на деца: два прохода

`reconcileChildren` на списък от елементи работи на два прохода, за да е бърз в честия случай и правилен в редкия:

1. По позиция. React върви едновременно по старите fiber-и и новите елементи. Докато `key` и `type` съвпадат на същата позиция, преизползва fiber-а и продължава. Спира при първото несъответствие. При списъци без промяна в реда това е целият алгоритъм.
2. По map с key. Остатъкът от старите fiber-и влиза в `Map` по `key` (или по индекс, ако няма key). За всеки оставащ нов елемент React търси в map-а: намерен означава преизползване, ненамерен означава нов fiber с `Placement`. Накрая всичко, което е останало в map-а, се изтрива. Елемент, който е намерен, но стои преди предишния намерен елемент в стария ред, също получава `Placement`, защото DOM възелът му трябва да се премести.

React нарочно не прави пълен diff на дървета (който е O(n³)), а сравнява ниво по ниво и само между братя. Елемент, преместен в друг родител, винаги е изтриване плюс създаване.

## Защо index като key е проблем

Без `key` React ползва индекса. При добавяне в началото на списъка всеки елемент се измества с една позиция, затова всеки стар fiber получава props на друг елемент. Последствията:

- Всеки компонент се рендерира отново, макар че "същите" елементи са на екрана. При дълги списъци това е цялата цена на пълен рендер.
- Състоянието остава при позицията. Поле за писане на позиция 0 запазва текста си, но вече показва друг елемент. Чекбокс остава отметнат на грешния ред.
- DOM възлите се пренаписват текст по текст вместо един възел да се вмъкне.

Със стабилен `key` (id от базата, не `Math.random()` и не индекс) React намира същия fiber, преизползва и състоянието, и DOM възела, и прави точно една вмъкваща операция.

## Защо фазата е чиста и прекъсваема

Всичко, което render фазата прави, е върху workInProgress дървото (виж [Double Buffering](Double_Buffering.md)) и върху нови DOM възли, които още не са в документа. Нищо от това не се вижда. Ако по средата дойде по-важно обновление, React може да спре след която и да е единица работа ([Time Slicing](Time_Slicing.md)), да изхвърли частично готовото дърво и да започне наново. За да е безопасно, компонентите трябва да са чисти функции: същият вход, същият изход, без странични ефекти. Render фазата може да извика компонента ти два пъти, без резултатът от първото извикване да стигне до екрана. Ако вътре пишеш в localStorage или правиш заявка, ще го направиш два пъти.

## Капани

- Мутация на state или props в render не е просто лош стил: `pendingProps === memoizedProps` остава вярно и React прави bailout, въпреки че "си променил нещо".
- `key` трябва да е уникален между братя, не глобално. Два различни списъка могат да имат `key="1"`.
- Смяна на `key` на компонент нарочно го размонтира и монтира отново. Това е валиден трик за "нулиране" на формуляр.
- Условен рендер `cond ? <A/> : <B/>` на една позиция винаги е изтриване и създаване, защото `type` е различен.
