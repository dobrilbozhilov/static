# Профилиране

Профилирането е единственият начин да разбереш къде наистина отива времето. Догадките за производителност са почти винаги грешни: компонентът, който "изглежда тежък", често е безобиден, а бавното нещо е ред, който се рендерира 300 пъти заради един забравен `memo`. React DevTools Profiler показва какво е рендерирал React и защо, Chrome Performance показва какво е правил браузърът около това.

## Аналогия: лекар с рентген

Добрият лекар не оперира по усещане. Прави снимка, вижда къде точно е проблемът и чак тогава решава. Profiler-ът е рентгенът: показва кой компонент колко време е отнел и защо изобщо се е рендерирал. Правилото е винаги едно: измери, намери, поправи, измери пак.

## React DevTools Profiler

Инсталирай разширението React Developer Tools (Chrome, Firefox, Edge). В DevTools се появява таб "Profiler". Работи така:

1. Натисни Record (кръгчето), направи действието, което те интересува (напиши в полето, отвори модала), натисни Stop.
2. Горе се появява лента с commit-ове: всеки бар е един commit (виж [Commit Phase](Commit_Phase.md)), височината е продължителността му.
3. В настройките (зъбното колело) включи "Record why each component rendered while profiling". Без тази опция панелът "Why did this render?" остава празен.

## Демо: четене на Profiler

Разгледай последователността от commit-ове: commit 2 е проблемът (Chart се рендерира при всяка буква без промяна в props), commit 3 е същото действие след `memo`, commit 4 е скъп, но честен (данните наистина са нови), commit 5 е как трябва да изглежда евтино обновление.

## Как се чете flamegraph

- Всеки ред е ниво от дървото: горе е коренът, под него децата му. Редът на компонентите отляво надясно е редът в дървото.
- Ширината е времето: колко е отнел компонентът заедно с децата си в този commit. Собственото му време (self) е разликата между неговата ширина и сумата на децата.
- Цветът показва относителната тежест: по-наситен означава по-дълго спрямо другите в същия commit.
- Сивите компоненти не са рендерирани в този commit. React ги е прескочил чрез bailout или `memo`.
- Клик върху компонент го "увеличава" (zoom) и показва вдясно продължителността му във всеки commit, плюс "Why did this render?".

Ranked изгледът подрежда само рендерираните компоненти по self време, от най-бавния надолу. Полезен е, когато дървото е дълбоко и flamegraph-ът е труден за четене: първите три реда са кандидатите за оптимизация.

## Why did this render?

Типичните причини, които панелът показва:

| Причина | Какво значи | Какво да провериш |
|---|---|---|
| Props changed: (data, onSelect) | Родителят е подал нови референции | дали са нови по съдържание или само по референция (виж [React.memo](React_memo.md)) |
| Hook 2 changed | Вторият hook в компонента (по ред на извикване) е сменил стойността си | setState в този компонент |
| The parent component rendered | Няма промяна в props и state, просто родителят се рендерира | кандидат за `memo` или за преместване на state надолу |
| Context changed | Стойността на consumed context е нова | дали provider-ът не подава нов обект всеки рендер |
| First render (mount) | Първо показване | нищо, нормално е |

Какво да търсиш в един запис:

- Компоненти, които се рендерират с "The parent component rendered" и са широки: тук `memo` или преструктуриране носи най-много (виж [Кога се пререндерира](Rerenders.md)).
- Един много дълъг commit (над 16 ms): нещо блокира кадъра. Виж кой компонент е най-широк.
- Много малки commit-ове един след друг при едно действие: липсва batching или има верига от ефекти, които викат setState един след друг (виж [Automatic Batching](Automatic_Batching.md)).
- Компонент, който се рендерира при всяко натискане на клавиш, въпреки че е далеч от полето.

## Profiler компонентът в код

Същите измервания могат да се събират програмно, например за да се пращат в аналитика:

```jsx
import { Profiler } from 'react';

function onRender(id, phase, actualDuration, baseDuration, startTime, commitTime) {
  // phase: "mount" | "update" | "nested-update"
  // actualDuration: време за този рендер; baseDuration: оценка без мемоизация
  if (actualDuration > 16) console.warn(`${id} ${phase}: ${actualDuration.toFixed(1)} ms`);
}

<Profiler id="Dashboard" onRender={onRender}>
  <Dashboard />
</Profiler>
```

`baseDuration` е интересна: това е колко би струвал рендерът, ако нищо не беше мемоизирано. Голяма разлика между `baseDuration` и `actualDuration` значи, че мемоизацията работи.

## Chrome Performance

Profiler-ът вижда само React. Chrome DevTools, таб Performance, показва цялата картина: мрежа, парсване на JS, layout, paint, garbage collection.

- Натисни Record, направи действието, Stop. Горе е времевата линия с кадри, долу Main нишката като flamegraph на функции.
- Червени триъгълници и секцията Long Tasks маркират задачи над 50 ms: през тях страницата не реагира. Виж [Кадри и рендериране](Rendering_Pipeline.md).
- Цветовете: жълто е scripting (твоят и React кодът), лилаво е rendering (style, layout), зелено е painting. Много лилаво след React commit значи скъп layout, обикновено от прекалено много DOM (виж [Виртуализация](Virtualization.md)).
- В development режим React добавя User Timings (⚛ маркери) в Timings лентата: вижда се кой компонент кога се рендерира и commit-ва, в контекста на всичко останало.
- Bottom-Up табът подрежда функциите по self време, както Ranked в React Profiler.

Chrome Performance е и мястото, където се вижда парсването на bundle-а при зареждане (виж [Code Splitting](Code_Splitting.md)).

## Development срещу production

Development build-ът на React е значително по-бавен: проверки на props, предупреждения, Strict Mode двоен рендер, user timings. Абсолютните числа от dev са безполезни за сравнение с production, но относителните (кой компонент е най-бавен, колко пъти се рендерира) са верни. За реални числа в production има `react-dom/profiling` build, който пази Profiler API-то, но маха останалия dev overhead; в Vite и webpack се включва с alias.

## Web Vitals накратко

Google измерва потребителското усещане с три числа: LCP (кога се появява най-голямото съдържание), CLS (колко скача layout-ът) и INP (Interaction to Next Paint: колко време минава от клик или клавиш до следващия кадър). INP е метриката, пряко свързана с React: дълги commit-ове, тежки ефекти и неразделена работа го влошават. Целта е под 200 ms за 75 % от взаимодействията. Профилирането по-горе е как се стига дотам.

## Чеклист

1. Измери: запиши Profiler сесия на конкретното бавно действие, не на "цялото приложение".
2. Намери: Ranked изглед, първите три компонента, "Why did this render?" за всеки.
3. Поправи едно нещо: `memo`, преместване на state, виртуализация, code splitting, `useTransition`.
4. Измери пак със същото действие. Ако числата не са мръднали, върни промяната.
5. Запиши резултата в коментар до оптимизацията, за да знае следващият защо е там.

## Капани

- Профилиране с отворени други табове, разширения или при зареждане на батерия дава шум. Повтори два-три пъти.
- Profiler-ът не записва commit-ове, в които нищо не е рендерирано, затова "липсващ" commit понякога е добра новина.
- Производителността на твоя лаптоп не е производителността на потребителя. Chrome има CPU throttling (4x, 6x) в Performance панела.
- Оптимизация без измерване преди и след е вяра, не инженерство.
