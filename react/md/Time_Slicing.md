# Time Slicing

Time slicing (нарязване на времето) е начинът, по който React разделя дълъг рендер на малки порции от по около 5 милисекунди и между тях връща контрола на браузъра. Така докато React подготвя голямо дърво, браузърът продължава да рисува анимации, да приема клавиши и да скролира. Тази страница показва с истинско измерване какво се случва с кадрите и с писането в поле, когато има и когато няма нарязване.

## Аналогия: касиерка с дълга опашка

Представи си касиерка, на която един клиент дава 600 продукта за сканиране. Ако тя сканира всичките наведнъж, всички останали на опашката чакат две минути, дори онзи, който иска само да попита къде е тоалетната. Умната касиерка сканира десетина продукта, поглежда дали някой има бърз въпрос, отговаря му и продължава. Големият клиент приключва почти по същото време, а никой не стои замръзнал на опашката.

Браузърът е опашката, клавишите и анимациите са бързите въпроси, а React е касиерката. Time slicing е навикът "сканирай малко, погледни наоколо, продължи".

## Бюджетът: 16.7 ms на кадър, 5 ms на порция

Екранът се опреснява 60 пъти в секунда, тоест на всеки 16.7 милисекунди браузърът трябва да нарисува нов кадър. В този бюджет влизат и JavaScript, и стил, и layout, и рисуване. Ако един JavaScript цикъл продължи 1200 ms, браузърът пропуска около 70 кадъра: анимациите замръзват, а буквите, които пишеш, се появяват накуп в края.

React си дава бюджет от 5 ms за порция работа. След всяка единица работа (един fiber възел, виж [Свързан списък](Linked_List.md)) проверява колко време е минало:

```js
const frameYieldMs = 5;
let startTime = 0;

function shouldYield() {
  return performance.now() - startTime >= frameYieldMs;
}

function workLoop() {
  startTime = performance.now();
  while (nextUnitOfWork !== null && !shouldYield()) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork !== null) scheduleNextSlice(workLoop);  // има още: продължи след като браузърът подиша
  else commitRoot();
}
```

Това е възможно само защото обхождането не е рекурсивно: `nextUnitOfWork` помни докъде е стигнал React, а call stack-ът е празен между порциите.

## Демо: гледай кадрите

Какво да забележиш: общото време на работата е почти същото в двата режима. Time slicing не прави изчислението по-бързо, а го прави прекъсваемо. В синхронния режим има един кадър от над 1000 ms, в нарязания има много кадри от по 16 до 20 ms. Отговорите на клавишите се обработват в паузите между порциите.

## Как React връща контрола: MessageChannel

След като порцията свърши, React трябва да каже на браузъра "сега ти, после пак аз". Има три на пръв поглед очевидни начина и React не ползва нито един от първите два:

| Механизъм | Защо не / защо да |
|---|---|
| `setTimeout(fn, 0)` | Браузърите закръглят към минимум 4 ms след няколко вложени извиквания. При 5 ms порции това губи почти половината време. |
| `requestAnimationFrame` | Вика се само преди кадър и спира изцяло в скрит таб. Работата на React не е свързана с рисуването. |
| `MessageChannel` | Съобщението се обработва като нова макро задача веднага след текущата, без закръгляне и независимо от кадрите. Това ползва React Scheduler. |

```js
const channel = new MessageChannel();
channel.port1.onmessage = workLoop;          // следващата порция тръгва като нова задача

function scheduleNextSlice() {
  channel.port2.postMessage(null);            // "сложи ме на опашката, след текущата задача"
}
```

Между две такива задачи браузърът е свободен: изпълнява чакащите event handler-и (клавиши, кликове), минава през микро задачите и ако е време за кадър, рисува. Подробно за опашките на страницата [Event Loop](Event_Loop.md) и за кадрите на [Кадри и рендериране](Rendering_Pipeline.md). В Node и в стари браузъри без `MessageChannel` scheduler-ът пада на `setTimeout`.

## Кога работи и кога не

Time slicing реже между fiber възлите, не вътре в тях. Това има две последствия:

- Помага, когато има много компоненти, всеки от които е сравнително бърз: голяма таблица, дълъг списък, дълбоко дърво. Хиляда компонента по 1 ms стават 200 порции по 5 ms.
- Не помага за един бавен компонент. Ако `beginWork` на един компонент прави синхронно изчисление от 300 ms, тези 300 ms са една неделима единица и кадърът ще замръзне. Решението там е `useMemo`, Web Worker или да разбиеш изчислението.

Освен това нарязването е включено само за обновления с нисък приоритет. Обновление от клик (SyncLane) се рендерира на един дъх, защото потребителят чака точно него. Кое обновление в коя лента попада е темата на [Concurrent React](Concurrent_React.md), а как да кажеш "това не е спешно" се вижда на [useTransition](useTransition.md).

## Капани

- Не очаквай по-бърз резултат. Общото време е същото или малко по-дълго. Печалбата е, че екранът остава жив.
- Прекъснат рендер може да бъде изхвърлен и започнат наново. Компонентът ти може да бъде извикан повече пъти, отколкото пъти стига до екрана. Render трябва да е чист.
- Браузърната конзола със `console.log` в render е подвеждаща при слайсване: ще видиш повторения, които не са бъг.
- Scheduler-ът е отделен пакет (`scheduler`) и работи и извън React, но API-то му не е публично стабилно.
