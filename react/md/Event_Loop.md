# Event Loop

JavaScript в браузъра работи на една нишка: в даден момент се изпълнява точно едно нещо. Всичко, което изглежда едновременно (таймери, заявки към сървър, кликове), минава през една проста машина, наречена event loop: стек за текущата работа, опашка за чакащата и правило кога се взема следващото. Разбираш ли тази машина, разбираш защо React реже рендера на порции, защо `setTimeout(fn, 0)` не е "веднага" и защо тежък цикъл замразява цялата страница.

## Аналогия: един готвач, една печка

Представи си кухня с един готвач и една печка. Готвачът може да готви само едно ястие в момента (това е call stack-ът). На стената има бележник с поръчки (опашката със задачи). Когато готвачът свърши ястие, поглежда бележника и взема следващата поръчка. Никога не прави две неща едновременно.

Но готвачът има помощници, които не готвят: фурната с таймер, куриерът, който носи продукти, звънецът на вратата. Готвачът им казва "фурна, звънни след 10 минути" и продължава да работи. Когато фурната звънне, тя не прекъсва готвача: само записва "извади хляба" в бележника. Готвачът ще го извади, когато свърши текущото ястие. Ако текущото ястие отнема два часа, хлябът ще чака два часа. Помощниците са Web APIs. Бележникът е task queue. Правилото "свърши текущото, после погледни бележника" е event loop.

## Частите

| Част | Какво е | Кой я управлява |
|---|---|---|
| Call stack | Стек от извиканите функции. Най-горната се изпълнява сега. | JavaScript engine (V8) |
| Heap | Паметта с обектите. Не участва в реда, само пази данни. | JavaScript engine |
| Web APIs | Таймери, `fetch`, DOM събития, `requestAnimationFrame`. Работят извън JavaScript нишката. | Браузърът (C++, други нишки) |
| Task queue | Опашка от callback-и, готови за изпълнение (макрозадачи). | Браузърът |
| Microtask queue | Опашка с предимство за Promise callback-и. Виж [Микро и макро задачи](Microtasks.md). | JavaScript engine |
| Event loop | Цикълът: стекът празен ли е? Ако да, изпразни микрозадачите, рисувай ако трябва, вземи една задача. | Браузърът |

## Call stack

Всяко извикване на функция слага нов frame най-отгоре в стека. Когато функцията върне, frame-ът се маха. Стекът има ограничен размер: рекурсия без край го препълва.

```js
function a() { b(); }
function b() { c(); }
function c() { throw new Error('къде съм?'); }
a();
// Error: къде съм?
//   at c   <- най-отгоре в стека
//   at b
//   at a
```

Това, което виждаш като stack trace, е снимка на call stack-а. Ако `c` извика `a` отново, стекът расте до "Maximum call stack size exceeded".

Важното за event loop: докато стекът не е празен, нищо отвън не може да влезе. Нито клик, нито таймер, нито отговор от сървъра.

## Web APIs не са JavaScript

`setTimeout`, `fetch`, `addEventListener` не са част от езика. Браузърът ги дава на JavaScript като услуги. Когато извикаш `setTimeout(cb, 100)`, JavaScript предава `cb` на браузъра и продължава веднага. Браузърът брои 100 ms в собствена нишка. Когато изтекат, не изпълнява `cb`: само го слага в task queue. Оттам `cb` ще влезе в стека, когато стекът е празен.

Затова 100 ms означава "не по-рано от 100 ms". Ако в момента тече тежък цикъл, `cb` ще чака колкото трябва.

## Правилото на event loop

```js
// Псевдокод на това, което браузърът прави вечно
while (true) {
  const task = taskQueue.takeOne();   // чака, ако няма
  run(task);                          // стекът расте и се изпразва
  runAllMicrotasks();                 // докрай, включително новите
  if (timeToRender()) renderFrame();  // около 60 пъти в секунда
}
```

Три следствия:

1. Една задача винаги се изпълнява докрай. Браузърът не прекъсва JavaScript по средата.
2. Рендерът се случва между задачите. Задача от 500 ms означава 500 ms без нов кадър.
3. Дори `setTimeout(fn, 0)` е "сложи fn в опашката": минимум една обиколка на цикъла по-късно. Браузърите освен това добавят поне 4 ms, когато таймерите са вложени над 4-5 нива. Затова React не ползва `setTimeout` за планиране (виж [Кадри и рендериране](Rendering_Pipeline.md)).

## Защо дълъг синхронен код замразява страницата

В сценария "Клик по време на дълъг цикъл" кликът пристига, докато `heavy()` е в стека. Браузърът го записва като задача, но задачата чака, докато стекът се изпразни. Потребителят натиска бутона и нищо не се случва две секунди. Същото важи за скрол, за писане в поле и за анимациите.

Голям React рендер в стария синхронен режим беше точно такава задача: `render` на хиляда компонента в една непрекъсната функция. Отговорът на React е да раздели работата на порции по 5 ms и между тях да върне контрола на event loop, така че чакащите кликове да се обработят. Това е [Time Slicing](Time_Slicing.md), а причината то да е възможно е [свързаният списък](Linked_List.md) от fiber възли.

## Node.js

В Node.js няма браузър, но принципът е същият: една JavaScript нишка, библиотека на C (libuv) за таймери, файлове и мрежа, и event loop, който подава готовите callback-и. Node има няколко фази в цикъла (timers, poll, check за `setImmediate`), а `process.nextTick` е опашка с предимство дори пред микрозадачите. Идеята "стекът трябва да е празен, за да влезе нещо отвън" важи еднакво.

## Капани

- `setTimeout(fn, 0)` не изпълнява `fn` веднага и не гарантира "след 0 ms". Гарантира само "не преди".
- Два таймера с еднакво време се изпълняват в реда на създаване, но между тях могат да влязат други задачи.
- `alert`, `confirm` и синхронният `XMLHttpRequest` блокират стека. Избягвай ги.
- Web Worker е истинска втора нишка със собствен event loop: тежки изчисления отиват там, не в main thread.
