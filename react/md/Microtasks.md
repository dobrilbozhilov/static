# Микро и макро задачи

Опашката със задачи от предишната страница всъщност е две опашки. Голямата (макрозадачи) държи таймери, кликове и мрежови отговори. Малката (микрозадачи) държи Promise callback-и, `await` продължения и `queueMicrotask`. Малката има абсолютно предимство: преди браузърът да вземе следващата макрозадача или да нарисува кадър, той изпразва микрозадачите докрай. Редът на изхода в почти всяка задача за интервю зависи точно от това правило.

## Аналогия: "докато си тук, довърши и това"

Готвачът свършва ястие и тръгва към бележника с поръчки. Но шефът го спира: "Докато си тук, довърши и тези малки неща." Малките неща са микрозадачите. Готвачът не може да вземе нова поръчка, докато списъкът с малки неща не е празен. И ако докато ги прави се появят нови малки неща, прави и тях. Чак след това поглежда бележника. Ако списъкът с малки неща никога не свършва, готвачът никога не стига до бележника и кухнята спира.

## Кое къде отива

| API | Опашка | Бележка |
|---|---|---|
| `setTimeout`, `setInterval` | макро | минимум 4 ms при вложени извиквания |
| DOM събития (click, input, scroll) | макро | всяко събитие е отделна задача |
| `fetch` отговор, `XMLHttpRequest` | макро | самото resolve-ване идва като задача, после `.then` е микро |
| `MessageChannel`, `postMessage` | макро | без 4 ms праг; React scheduler го ползва |
| `requestAnimationFrame` | нито едно | отделна опашка, изпълнява се точно преди рендер |
| `Promise.then / catch / finally` | микро | дори Promise-ът да е вече готов |
| `await` | микро | остатъкът от функцията е микрозадача |
| `queueMicrotask(fn)` | микро | директно, без Promise |
| `MutationObserver` | микро | известия за промени в DOM |
| `process.nextTick` (Node) | преди микро | опашка с още по-високо предимство |

## Точното правило

```js
// Какво прави event loop след всяка задача
function afterTask() {
  while (microtasks.length > 0) {       // не "за всяка", а "докато има"
    const m = microtasks.shift();
    run(m);                             // m може да добави нови микрозадачи
  }
  // чак сега: рендер (ако е време) и следваща макрозадача
}
```

Две следствия, които хващат хората неподготвени:

- Микрозадача, добавена от микрозадача, се изпълнява в същата обиколка, преди следващата макрозадача. Опашката се изпразва докрай, не само това, което е било в нея в началото.
- Микрозадачите се изпълняват и след всеки callback, който браузърът извиква от празен стек, не само след "задача". Например след всеки event listener при истински клик (но не при `element.click()` от код, защото там стекът не е празен между listener-ите).

## await е микрозадача

```js
async function load() {
  console.log('преди');        // синхронно, в стека на извикващия
  const data = await fetch(url); // тук функцията "излиза" и връща Promise
  console.log('след');         // това е микрозадача, когато Promise-ът е готов
}
```

`async` функция се изпълнява синхронно до първия `await`. Там тя спира, връща Promise на извикващия и останалата част се опакова като микрозадача, която ще се изпълни, когато стойността след `await` е готова и стекът е празен. Дори `await 1` минава през микроопашката: затова "след" никога не е преди кода, който следва `load()` в извикващия.

## Защо безкрайни микрозадачи са опасни

```js
function spin() {
  queueMicrotask(spin);   // всяка микрозадача добавя нова
}
spin();                   // страницата замръзва завинаги, без грешка
```

Макрозадачите поне пускат рендер помежду си. Микрозадачите не: браузърът няма кога да нарисува кадър, докато опашката не се изпразни, а тя не се изпразва. Същият ефект има и дълга верига от `Promise.resolve().then(...)` с тежка работа във всяко звено. Ако имаш много работа на парчета и искаш страницата да диша, парчетата трябва да са макрозадачи.

## Какво значи това за React

- `setState` в `Promise.then` или след `await` в React 18 се събира в един рендер заедно с другите `setState` в същата микрозадача. Виж [Automatic Batching](Automatic_Batching.md).
- React scheduler нарочно планира следващата порция работа като макрозадача през `MessageChannel`. Ако беше микрозадача, браузърът нямаше да рисува между порциите и целият смисъл на [Time Slicing](Time_Slicing.md) щеше да изчезне.
- `useEffect` callback-ите не са микрозадачи и не са Promise. React ги пуска след paint като отделна задача (или синхронно преди следващо discrete събитие). Виж [useLayoutEffect и useEffect](Effects_Timing.md).
- Ако в event handler направиш `await` и после `setState`, обновлението става в друга задача: handler-ът вече е приключил и React го третира като обновление извън събитие.

## Капани

- `Promise.resolve().then(fn)` никога не изпълнява `fn` синхронно, дори Promise-ът да е готов.
- Грешка в микрозадача не спира останалите: следващата се изпълнява, а грешката става unhandled rejection.
- `setTimeout(fn, 0)` след `Promise.then(fn2)` винаги дава `fn2` преди `fn`, независимо от реда на извикване.
- В Node.js `process.nextTick` е преди Promise callback-ите, а `setImmediate` е макрозадача в отделна фаза. Не бъркай двете среди.
