# Какво е Fiber

Fiber е името на ядрото на React от версия 16 нататък: едновременно структура от данни (един обект за всеки компонент или елемент на екрана) и начин на работа (всеки такъв обект е малка порция работа, която може да се свърши, спре и продължи). Тази страница обяснява защо React си пренаписа ядрото, какво има в един fiber възел и защо това има значение за теб.

## Аналогия: четене на книга на глас

Представи си, че някой ти чете приказка на глас и правилото е, че не може да спре, докато не стигне края. Ако по средата те заболи коремът, трябва да чакаш. Така работеше React до версия 15: щом започне да изчислява какво да покаже, продължава до край, с рекурсия, в една непрекъсната JavaScript функция. При малко приложение това е милисекунда и никой не забелязва. При голяма таблица с хиляди редове става 200 или 500 милисекунди, през които браузърът не може да направи нищо друго: не реагира на писане, не анимира, не скролира.

С Fiber четецът чете по една страница, после поглежда дали някой има нужда от нещо. Ако ти пишеш в поле, той първо показва буквата, после продължава приказката откъдето е спрял. За да може да спре и да продължи, му трябва отметка. Fiber възелът е точно тази отметка.

## Проблемът преди Fiber

Старият reconciler (наричан stack reconciler) обхождаше дървото от компоненти с обикновена рекурсия: `render(App)` вика `render(List)`, която вика `render(Item)` за всеки елемент и така нататък. Рекурсията живее в call stack-а на JavaScript, а call stack-ът не може да бъде замразен по средата и възстановен по-късно. Значи или цялата работа се свършва на един дъх, или нищо.

```jsx
// Така изглеждаше идеята в React 15 (опростено)
function reconcile(element) {
  const output = element.type(element.props);   // рендерира компонента
  for (const child of output.children) {
    reconcile(child);                             // рекурсия: няма връщане назад, докато не свърши
  }
}
```

Тази форма има три последствия:

- Нищо не може да прекъсне рендера. Клик или натиснат клавиш чака.
- Всички обновления са еднакво важни. Няма как анимация да получи предимство пред зареждане на данни.
- Няма как половината работа да се изхвърли, ако междувременно е дошло нещо по-важно.

## Какво е един fiber възел

Fiber е обикновен JavaScript обект. React създава по един за всеки елемент, който рендерираш: за `<App/>`, за `<div>`, за `<Item key="a"/>`, дори за текста вътре в `<h1>`. Възлите са свързани помежду си с указатели и образуват дърво, което повтаря формата на твоя JSX, но пази и още нещо: какво е било при предишния рендер, какво трябва да стане при този и колко е спешно.

<div data-widget="fiber-node"></div>

Най-важните полета, групирани по смисъл:

| Група | Полета | За какво служат |
|---|---|---|
| Какво е | `tag`, `type`, `key`, `stateNode` | Вид на възела, какво рендерира, ключ, връзка към DOM или инстанция |
| Къде е | `return`, `child`, `sibling` | Указатели към родител, първо дете и следващ брат; виж [Свързан списък](Linked_List.md) |
| Какво носи | `pendingProps`, `memoizedProps`, `memoizedState` | Новите props, старите props, състоянието от последния рендер |
| Какво да се направи | `flags`, `subtreeFlags`, `deletions` | Отбелязани промени за commit фазата: вмъкни, обнови, изтрий |
| Колко е спешно | `lanes`, `childLanes` | Приоритети на чакащите обновления; виж [Concurrent React](Concurrent_React.md) |
| Двойникът | `alternate` | Същият възел в другото дърво; виж [Double Buffering](Double_Buffering.md) |

За функционален компонент `memoizedState` е свързан списък от hook обекти, в реда, в който си извикал `useState`, `useEffect` и т.н. Затова hooks не бива да се викат условно: React ги разпознава по позиция, не по име.

## Fiber като единица работа

Второто значение на думата е по-важното. Един fiber е и една порция работа: "вземи този възел, извикай компонента му, сравни резултата с предишния, отбележи какво се е променило, подготви децата". Това е функцията `performUnitOfWork`. React я вика в цикъл и след всяка порция може да провери дали има нещо по-спешно.

```js
// Сърцето на React, силно опростено
let nextUnitOfWork = root;

function workLoop(deadline) {
  while (nextUnitOfWork && !shouldYield()) {   // работи, докато има работа и време
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  if (nextUnitOfWork) scheduleCallback(workLoop); // има още: продължи по-късно
  else commitRoot();                              // всичко е готово: приложи към DOM
}
```

Ключовата дума е `shouldYield()`. Тя пита "минаха ли около 5 милисекунди" и ако да, цикълът спира, връща контрола на браузъра и се записва на опашката за по-късно. Къде точно спира няма значение, защото следващият възел е записан в `nextUnitOfWork`, а всички връзки са в самите fiber обекти, не в call stack-а. Подробно: [Time Slicing](Time_Slicing.md).

## Двете фази

Работата на React по едно обновление се дели на две ясни части, и това разделение е възможно само заради fiber:

1. [Render Phase](Render_Phase.md): изчислява какво трябва да се промени. Може да се прекъсва, спира и рестартира. Не докосва DOM. Резултатът е ново дърво с отбелязани промени.
2. [Commit Phase](Commit_Phase.md): прилага промените към DOM на един дъх, без прекъсване, и пуска ефектите.

Ако render фазата се прекъсне и после се изхвърли, потребителят не вижда нищо, защото екранът не е пипан. Това е цялата идея: подготвяй колкото искаш дълго и на порции, прилагай бързо и наведнъж.

## Какво означава това за теб

- Компонентът ти може да бъде извикан, без резултатът да стигне до екрана, ако рендерът бъде изхвърлен. Затова render трябва да е чиста функция: без странични ефекти, без мутации.
- В Strict Mode React нарочно извиква компонентите два пъти при разработка, за да хване нечисти рендери.
- `useEffect` се изпълнява в commit фазата или след нея, не по време на рендер. Виж [useLayoutEffect и useEffect](Effects_Timing.md).
- Приоритетите не са магия: те са числа в `lanes` на fiber възлите. `useTransition` само казва "тези обновления са с нисък приоритет".
