# Кадри и рендериране

Екранът се обновява около 60 пъти в секунда. Между две обновявания има 16.7 милисекунди и в тях браузърът трябва да събере всичко: твоя JavaScript, микрозадачите, пресмятането на стиловете и позициите, рисуването. Ако не се събере, кадърът се пропуска и окото вижда накъсване. Тази страница показва какво точно става в един кадър, защо React планира работата си с `MessageChannel` и кои неща са евтини за анимиране.

## Аналогия: кино

Филмът е поредица от картинки, показвани толкова бързо, че мозъкът вижда движение. Ако прожекционният апарат закъснее с една картинка, кадърът "увисва" и всички в залата го забелязват. Браузърът е апарат с 60 картинки в секунда. Твоят JavaScript е човекът, който подготвя следващата картинка: има 16.7 ms. Ако се забави, картинката просто не излиза навреме, а апаратът показва старата още веднъж.

## Какво прави браузърът в един кадър

| Стъпка | Какво става | Кога става |
|---|---|---|
| Task (JavaScript) | Event handler, таймер, React render | Когато event loop вземе задача |
| Микрозадачи | Promise callback-и, `await` | Веднага след задачата, докрай |
| `requestAnimationFrame` | Callback-ите, регистрирани с rAF | Точно преди стъпките за рисуване |
| Style | Кои CSS правила важат за всеки елемент | Само ако нещо е "мръсно" |
| Layout | Размери и позиции (геометрия) | Ако геометрията е пипната |
| Paint | Рисуване на пикселите по слоеве | Ако нещо визуално се е променило |
| Composite | Слоевете се слепват в крайна картинка | Compositor thread, често без main thread |

Style, layout, paint и composite се наричат pixel pipeline. Промяна на `width` минава през всичките четири. Промяна на `transform` или `opacity` прескача layout и paint и отива направо в composite, което е десетки пъти по-евтино.

## requestAnimationFrame

`rAF` казва на браузъра "извикай тази функция точно преди следващото рисуване". Това е единственото място, където имаш гаранция, че промените ти ще влязат в идващия кадър, без да се пресмята междинно състояние.

```js
function animate(now) {
  box.style.transform = `translateX(${(now / 10) % 300}px)`;
  requestAnimationFrame(animate);   // регистрира се за следващия кадър
}
requestAnimationFrame(animate);
```

Защо не `setInterval(fn, 16)`? Защото интервалът не е синхронизиран с екрана: понякога ще смениш позицията два пъти в един кадър (загубена работа), понякога нито веднъж (прескок). Освен това rAF спира в скрит таб, което пести батерия, но е и причината React да не го ползва за планиране.

## Дълги задачи и INP

Задача над 50 ms се нарича long task. Докато тя тече, кликовете чакат, анимациите стоят, полетата не показват написаното. Метриката INP (Interaction to Next Paint) измерва точно това: колко време минава от действие на потребителя до следващия нарисуван кадър. Над 200 ms е "лошо".

CSS анимация, която променя само `transform` или `opacity`, обикновено се движи от compositor thread и продължава, докато JavaScript е блокиран. Това зависи от браузъра и от това дали елементът е в собствен слой. JS анимацията с rAF винаги спира: rAF callback-ът е част от кадъра, а кадър няма, докато стекът не е празен.

## Защо React планира с MessageChannel

React scheduler-ът трябва след всяка порция от 5 ms да пусне браузъра и после веднага да продължи. Три възможности:

| Вариант | Проблем |
|---|---|
| `requestAnimationFrame` | Не се вика в скрит таб. Обвързан е с кадъра: при 60 Hz максимум 60 порции в секунда, а и моментът "преди рисуване" е грешен за работа, която не е рисуване. |
| `setTimeout(fn, 0)` | След 4-5 вложени извиквания браузърът налага минимум 4 ms. При порции по 5 ms това е почти удвояване на времето. |
| `MessageChannel` | Макрозадача без минимално закъснение: следващото съобщение идва веднага след текущата задача, но браузърът все пак може да нарисува кадър между тях. |

```js
// Сърцето на scheduler-а, силно опростено
const channel = new MessageChannel();
let deadline = 0;
const yieldInterval = 5;

channel.port1.onmessage = () => {
  deadline = performance.now() + yieldInterval;   // нова порция от 5 ms
  const hasMore = workLoop();                       // работи до shouldYield()
  if (hasMore) channel.port2.postMessage(null);     // има още: планирай следваща порция
};

function shouldYield() {
  return performance.now() >= deadline;
}

function scheduleWork() {
  channel.port2.postMessage(null);
}
```

Между две съобщения стекът е празен, микрозадачите се изпразват, чакащите кликове се обработват и ако е време, браузърът рисува. Точно това е [Time Slicing](Time_Slicing.md).

## Layout thrashing

```js
// Бавно: всяко четене на offsetHeight принуждава браузъра да пресметне layout наново
for (const el of items) {
  el.style.height = el.offsetHeight * 2 + 'px';   // четене, после писане, после четене...
}

// Бързо: първо всички четения, после всички писания
const heights = items.map((el) => el.offsetHeight);
items.forEach((el, i) => { el.style.height = heights[i] * 2 + 'px'; });
```

Четене на геометрия (`offsetHeight`, `getBoundingClientRect`) след писане в стила принуждава синхронен layout. В цикъл това се нарича layout thrashing и е честа причина за дълги задачи. React commit фазата нарочно първо прави всички DOM промени, после пуска `useLayoutEffect`, където четеш: едно пресмятане вместо много. Виж [Commit Phase](Commit_Phase.md).

## Кои свойства са евтини

- `transform`, `opacity`: само composite. Подходящи за анимация.
- `color`, `background`, `box-shadow`: paint, без layout.
- `width`, `height`, `top`, `margin`, `font-size`: пълният pipeline. Избягвай да ги анимираш.
- `will-change: transform` подсказва на браузъра да сложи елемента в собствен слой. Ползвай го пестеливо: всеки слой е памет.

## Как да го видиш в DevTools

1. Performance таб, Record, направи действието, Stop.
2. Горе е лентата с кадрите: зелени са навреме, червените са пропуснати.
3. Main thread: дълги жълти блокове са JavaScript задачи. Над 50 ms са маркирани с червена шарка като long task.
4. Лилавото е style и layout, зеленото е paint. Ако лилавото се повтаря много пъти в една задача, имаш layout thrashing.
5. В React приложение в dev режим виждаш и User Timings с имена на компонентите.

## Капани

- Измервай в production build. Dev build на React е няколко пъти по-бавен.
- 120 Hz екрани имат 8.3 ms на кадър. Бюджетът ти е наполовина.
- `will-change` на всичко прави страницата по-бавна, не по-бърза.
- `setTimeout(fn, 16)` не е заместител на rAF.
- Четене на `scrollTop` в scroll handler след писане в стила е layout thrashing на всеки кадър.
