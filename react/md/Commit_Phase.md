# Commit Phase

Commit фазата е втората половина от работата на React: взема готовото workInProgress дърво с флаговете от [Render Phase](Render_Phase.md) и го прилага към истинския DOM. За разлика от render фазата тя е синхронна, не може да бъде прекъсната и винаги се довършва на един дъх. В нея се сменят DOM възлите, прикачат се ref-ове и се викат ефектите, в точно определен ред.

## Аналогия: преписване на чисто

Черновата може да се пише с дни, но преписването на чисто се прави наведнъж: ако спреш по средата, писмото ще е половин старо, половин ново и никой няма да може да го прочете. Същото е с DOM-а. Ако React спре по средата на commit, потребителят ще види брояч с новата стойност, но без новия ред под него, а event handler-ите ще сочат към стария state. Затова React не пуска браузъра между две DOM операции: прави всичко, после връща контрола.

## Защо commit е синхронен

Render фазата може да си позволи паузи, защото работи върху невидимо дърво. Commit фазата работи върху екрана. Ако React отстъпеше на браузъра по средата, той би нарисувал кадър с наполовина обновен DOM. Затова `commitRoot` е един непрекъснат JavaScript блок: започва след последния `completeWork` и свършва преди браузърът да получи шанс да рисува. Обикновено е много бърз, защото трудната част (кои възли да се променят) вече е изчислена; тук само се изпълняват готовите инструкции.

## Трите под-фази

`commitRoot` минава през дървото три пъти, всеки път само през клоните, в които `subtreeFlags` казва, че има работа:

| Под-фаза | Какво се случва | DOM е |
|---|---|---|
| Before mutation | `getSnapshotBeforeUpdate`; планира се изпълнението на passive ефектите | старият |
| Mutation | изтривания, вмъквания (`Placement`), обновяване на props (`Update`), cleanup на `useLayoutEffect`, откачане на ref | става новият |
| Layout | прикачане на ref, `useLayoutEffect`, `componentDidMount`, `componentDidUpdate` | новият |

Между mutation и layout има едно-единствено присвояване: `root.current = finishedWork`. Преди него `current` е старото дърво, за да могат cleanup функциите да виждат старите props и state. След него `current` е новото, за да могат `componentDidMount` и layout ефектите да виждат новото. Виж [Double Buffering](Double_Buffering.md).

След трите под-фази React връща контрола. Браузърът рисува. После, в отделна задача, се изпълняват passive ефектите: първо всички cleanup функции на `useEffect` от предишния рендер, после всички нови `useEffect`.

## Кога DOM-ът е актуален

Това е въпросът, който решава кой hook да ползваш:

- В render: DOM-ът е старият, а може и да не съответства на това, което изчисляваш, защото рендерът може да бъде изхвърлен. Не чети DOM тук.
- В `useLayoutEffect`: DOM-ът е новият, но още не е нарисуван. Можеш да мериш (`getBoundingClientRect`) и да промениш state; React ще рендерира синхронно и потребителят ще види само крайния резултат. Цената е, че забавяш кадъра.
- В `useEffect`: DOM-ът е новият и вече нарисуван. Ако тук мериш и променяш позиция, ще има трепване: един кадър със старата позиция, после с новата.

Подробно и с истински React в [useLayoutEffect и useEffect](Effects_Timing.md).

## Редът вътре в под-фазата

Във всяка под-фаза React обхожда дървото в дълбочина и обработва децата преди родителите. Това има практическо значение: `useLayoutEffect` на дете се изпълнява преди този на родителя, и `ref` на дете е прикачен, когато ефектът на родителя тече. Затова родител може да мери децата си в своя ефект. Cleanup функциите в mutation фазата също вървят деца преди родители, така че дете винаги "се разглобява" преди родителя си.

```jsx
function Parent() {
  const listRef = useRef(null);
  useLayoutEffect(() => {
    // Всички <Child/> вече са в DOM и техните layout ефекти са минали.
    console.log(listRef.current.children.length);
  });
  return <ul ref={listRef}>{items.map((i) => <Child key={i.id} {...i} />)}</ul>;
}
```

## Изтриванията

Fiber, който изчезва, не е в новото дърво и няма как да носи флаг. Вместо това родителят му получава `ChildDeletion` и масив `deletions`. В mutation фазата React минава през този масив и за всеки изтрит fiber обхожда цялото му поддърво: вика cleanup функциите на всички ефекти, `componentWillUnmount`, откача ref-овете и накрая маха само най-горния DOM възел с `removeChild` (децата му изчезват заедно с него).

## Капани

- `setState` в `useLayoutEffect` е законен, но води до втори синхронен рендер и commit преди paint. Прави го само когато междинното състояние наистина не бива да се вижда.
- Грешка в commit фазата (например в `useLayoutEffect`) не може да бъде "върната назад": DOM-ът вече е променен. React размонтира дървото до най-близкия error boundary.
- `useEffect` не е гарантирано "след paint" при всяко обновление: ако следващият рендер започне преди passive ефектите, React първо ги изпълнява синхронно (`flushPassiveEffects`), за да не изостават.
- Commit фазата е една за цялото дърво, а не по компонент: дълъг списък от `useLayoutEffect` със скъпи измервания бави целия кадър.
