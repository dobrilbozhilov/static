# Структура от данни: свързан списък

Fiber дървото не е масив от масиви. Всеки възел пази точно три указателя: `child` към първото си дете, `sibling` към следващия брат и `return` към родителя. Това превръща дървото в свързан списък, който може да се обхожда с обикновен цикъл вместо с рекурсия, и точно това позволява на React да спира по средата.

## Аналогия: нишка през мъниста

Представи си мъниста, нанизани на конец. Всяко мънисто знае кое е следващото, защото конецът минава през него. Ако спреш да броиш по средата, просто запомняш на кое мънисто си стигнал и после продължаваш. Не ти трябва да помниш целия път дотук.

При рекурсия е обратното: пътят дотук живее в call stack-а и ако го напуснеш, той изчезва. Затова React 15 не можеше да спира, а React с Fiber може: "на кое мънисто съм" е една променлива, `nextUnitOfWork`, а конецът са трите указателя във всеки fiber.

## Трите указателя

```text
            App
             │ child
             ▼
          Header ──sibling──▶ List
             │ child            │ child
             ▼                  ▼
            h1               Item a ──sibling──▶ Item b
```

- `child` сочи само първото дете. Нито `App`, нито `List` имат масив с децата си.
- `sibling` свързва децата на един родител във верига: `Header → List`, `Item a → Item b`.
- `return` сочи родителя и от двамата братя: `Header.return === App` и `List.return === App`.

Защо не масив? Защото с масив трябва да помниш индекс "докъде стигнах при този родител" за всяко ниво, което отново е стек. С `sibling` следващата стъпка винаги е записана в самия възел.

## Демо: обхождане стъпка по стъпка

Това е истинският алгоритъм от React (`performUnitOfWork`), с опростени имена. Следи как `nextUnitOfWork` винаги сочи точно един възел и как при всяка стъпка цикълът може да бъде спрян и продължен.

Редът, в който се случват нещата, е депт-фърст (в дълбочина): React слиза надолу по `child`, докато стигне листо, довършва го с `completeWork`, минава на `sibling`, а когато братята свършат, се качва по `return`. Родителят се довършва едва след всичките си деца, защото при `completeWork` на DOM елемент React сглобява DOM възела и прикачва готовите деца към него.

## Защо това прави паузата възможна

```js
let nextUnitOfWork = null;

function workLoop(deadline) {
  while (nextUnitOfWork && !shouldYield()) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }
  // Ако сме спрели по средата, nextUnitOfWork пази откъде да продължим.
}
```

Цялото състояние на обхождането е в една променлива. Между два завъртания на цикъла React може да върне контрола на браузъра, той да обработи клик, да нарисува кадър, и после React да продължи. На страницата [Time Slicing](Time_Slicing.md) ще видиш какво се случва с кадрите, когато това се прави и когато не се прави.

## Hooks също са свързан списък

Същата идея се ползва и на едно ниво по-надолу. `memoizedState` на функционален компонент не е масив от hooks, а свързан списък: всеки hook обект има `next` към следващия.

```js
// Опростено: какво пази fiber-ът за компонент с два hook-а
fiber.memoizedState = {
  memoizedState: 0,            // useState(0)
  queue: { pending: null },    // чакащи setState извиквания
  next: {
    memoizedState: { deps: [] }, // useEffect(fn, [])
    next: null,
  },
};
```

При всеки рендер React тръгва от началото на списъка и при всяко извикване на `useState` или `useEffect` взема следващия hook. Затова редът трябва да е еднакъв при всеки рендер: ако един път извикаш два hook-а, а друг път три, React ще даде на третото извикване чуждо състояние. Това е цялото обяснение на правилото "не викай hooks в условия и цикли".
