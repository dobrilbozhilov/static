# Concurrent React

Concurrent React е способността на React да работи по няколко обновления с различна важност, да прекъсва по-малко важното заради по-важното и да го започва отначало, без потребителят някога да види полуготов екран. Тази страница обяснява какво е lane (лента с приоритет), какво точно се случва при прекъсване и какво React гарантира и какво не.

## Аналогия: готвачът с голямото ястие

Готвач готви голяма тенджера супа, която отнема половин час. По средата влиза дете и иска чаша вода. Лошият готвач казва "чакай да стане супата". Добрият оставя лъжицата, налива водата за десет секунди и се връща към супата. Ако докато е наливал водата, някой е сменил рецептата (вече искат друга супа), той излива тенджерата и започва наново, защото старата работа не става.

React с конкурентен режим е добрият готвач. Супата е дългият рендер (например филтриране на голям списък), чашата вода е кликът, а смяната на рецептата е фактът, че след клика дървото е различно и старото workInProgress не може да се продължи.

Обърни внимание на три неща: кликът стига до екрана за няколко единици време, въпреки че го е заварил по средата на дълъг рендер; недовършеният рендер се изхвърля изцяло, а не се "кръпка"; и бавното обновление все пак стига до екрана, само по-късно.

## Какво е lane

Всяко обновление получава lane: един бит в 31-битово число. Битовете с по-малка стойност са с по-висок приоритет. Fiber възлите пазят `lanes` (какви обновления чакат по тях) и `childLanes` (какви чакат някъде в поддървото), така че React да знае през кои възли изобщо трябва да мине.

```js
// Опростено от ReactFiberLane.js
const SyncLane            = 0b0000000000000000000000000000010;
const InputContinuousLane = 0b0000000000000000000000000001000;
const DefaultLane         = 0b0000000000000000000000000100000;
const TransitionLane1     = 0b0000000000000000000000010000000;
// ... още transition lanes
const RetryLane1          = 0b0000001000000000000000000000000;
const IdleLane            = 0b0100000000000000000000000000000;
```

| Lane | Кой го създава | Поведение |
|---|---|---|
| SyncLane | `setState` в click, keydown, submit и други дискретни събития; `flushSync` | Рендерира се на един дъх, без нарязване, преди всичко друго |
| InputContinuousLane | `setState` в scroll, drag, mousemove, pointermove | Висок приоритет, но може да се слива със следващото такова събитие |
| DefaultLane | `setState` в `setTimeout`, `fetch().then`, `useEffect`, native event listener | Нормален приоритет, нарязва се |
| TransitionLane | `startTransition`, `useTransition`, `useDeferredValue` | Нисък приоритет, нарязва се, прекъсва се от всичко по-високо |
| RetryLane | Suspense, когато данните пристигнат | Повторен опит за рендер на спряно поддърво |
| IdleLane | Вътрешно, почти никога от твой код | Само когато няма нищо друго |

Защо битове, а не числа 1, 2, 3? Защото едно обновление може да чака в няколко ленти едновременно, а битовите операции (`lanes & SyncLane`, `lanes | TransitionLane`) са най-бързият начин да се пита "има ли нещо спешно тук". Няколко transition ленти има, за да може React да рендерира отделни transition-и независимо и да не чака един да приключи, за да започне друг.

## Entanglement: кога две ленти се слепват

Ако две обновления на едно и също състояние попаднат в различни ленти, React не може да ги рендерира отделно: второто зависи от първото. Тогава лентите се "заплитат" (entangle) и се обработват заедно. Същото става, когато transition рендер бъде прекъснат от sync обновление на същия компонент. Затова в демото transition-ът не просто продължава, а започва отначало върху новото current дърво.

## Задръжка и паралелност

Думата concurrent (конкурентен) често се бърка с parallel (паралелен). React работи в един thread. Нищо не се изпълнява едновременно. Конкурентност означава, че React може да спре една работа, да свърши друга и да се върне към първата. Това е като един човек, който редува две задачи, не двама души.

Какво React гарантира:

- Екранът винаги показва едно цяло, консистентно дърво. Няма момент, в който половината компоненти са с новото състояние, а другата половина със старото (това се нарича tearing).
- Sync обновленията стигат до екрана преди всички по-ниски ленти, дори ако са дошли по-късно.
- Обновления в една и съща лента се събират в един рендер (виж [Automatic Batching](Automatic_Batching.md)).

Какво React не гарантира:

- Че компонентът ти ще бъде извикан точно веднъж на обновление. При прекъсване може да бъде извикан пак.
- Че render фазата ще стигне до commit. Изхвърлен рендер не оставя следа.
- Че външни източници на данни (глобална променлива, store извън React) ще са консистентни по време на прекъснат рендер. За това има `useSyncExternalStore`, който принуждава sync рендер при промяна в store-а.

## createRoot срещу legacy

Всичко на тази страница важи само за `ReactDOM.createRoot`. Старият `ReactDOM.render` (legacy режим, премахнат в React 19) рендерира всяко обновление синхронно и докрай. Няма ленти, няма прекъсване, няма transition, няма automatic batching извън event handler-и. Ако мигрираш старо приложение, първата стъпка към всичко описано тук е смяната на root API-то.

```jsx
import { createRoot } from 'react-dom/client';

createRoot(document.getElementById('root')).render(<App />);
```

## Капани

- `console.log` в render ще показва повторения при прекъснат рендер. Това не е бъг, а признак, че рендерът е бил изхвърлен.
- Странични ефекти в render (запис в localStorage, мутация на обект извън компонента) ще се изпълнят и за изхвърлените рендери. Дръж ги в `useEffect`.
- Две transition-а на едно и също състояние се сливат: вторият не "отменя" първия, а го заменя. Резултатът винаги е последното състояние.
- Прекалено много sync обновления (например `setState` на всеки `mousemove` в sync лента) връщат старото поведение: никой transition не успява да завърши.
