# React.memo: плитко сравнение

`React.memo` увива компонент и казва на React: "ако props са същите като миналия път, не ме извиквай, покажи стария резултат". Звучи просто, но думата "същите" е цялата хитрост: React сравнява плитко, по референция, и затова един inline обект или стрелкова функция в JSX е достатъчен, за да направи мемоизацията безполезна.

## Аналогия: пазач с лични карти

Представи си пазач на вход, който пуска хората без проверка, ако са същите като вчера. Той не гледа лицата, гледа личните карти: ако картата е същата, минаваш. Числата, низовете и булевите стойности са като хора с една и съща карта за цял живот: `5` днес и `5` утре са един и същ човек. Обектите и функциите обаче получават нова лична карта всеки път, когато се създадат. `{ color: 'red' }` днес и `{ color: 'red' }` утре са двама различни души с еднакви дрехи. Пазачът (React.memo) не отваря чантата да види какво има вътре, той гледа само картата.

## Как работи shallowEqual

Когато родителят се рендерира, React стига до мемоизирания компонент в `beginWork` (виж [Render Phase](Render_Phase.md)) и преди да извика функцията му, сравнява новите props със старите:

```js
function shallowEqual(prev, next) {
  if (Object.is(prev, next)) return true;
  const prevKeys = Object.keys(prev);
  const nextKeys = Object.keys(next);
  if (prevKeys.length !== nextKeys.length) return false;
  for (const key of prevKeys) {
    if (!Object.hasOwn(next, key) || !Object.is(prev[key], next[key])) return false;
  }
  return true;
}
```

Три неща следват от този код:

- Сравнява се само едно ниво: всеки prop поотделно чрез `Object.is`. Няма рекурсия навътре в обектите.
- `Object.is` е почти като `===`, но `NaN` е равно на `NaN` и `+0` не е равно на `-0`.
- Ако един-единствен prop е различен, цялата проверка се проваля и компонентът се рендерира. Няма "частично" прескачане.

## Защо `{}` не е равно на `{}`

```js
Object.is({ a: 1 }, { a: 1 });       // false: два различни обекта в паметта
Object.is(() => {}, () => {});       // false: две различни функции
Object.is([1, 2], [1, 2]);           // false
Object.is('abc', 'abc');             // true: низовете се сравняват по стойност
Object.is(42, 42);                   // true
```

В JSX всеки рендер на родителя изпълнява тялото му отново. Всяко `style={{ color }}`, `onClick={() => ...}`, `items={data.filter(...)}` или `<Child><b>x</b></Child>` създава нов обект при всяко изпълнение. Детето получава нова референция, `shallowEqual` връща `false`, мемоизацията е счупена, без никой да е направил "грешка" в логиката.

## Демо: кой prop чупи мемоизацията

<div data-widget="memo-lab"></div>

Забележи, че `children` винаги чупи сравнението, когато е JSX, написан в родителя: всяко `<b>дете</b>` е `React.createElement(...)`, тоест нов обект. Единственият начин children да минат през memo е родителят да ги получи отвън (например от своя родител) и да ги подаде без промяна. Това е "lift content up" трикът от [Кога се пререндерира](Rerenders.md).

## Поправяне: стабилни референции

| Счупва memo | Стабилна версия |
|---|---|
| `style={{ color }}` | `const style = useMemo(() => ({ color }), [color])` или CSS клас |
| `onClick={() => save(id)}` | `const onClick = useCallback(() => save(id), [id])` |
| `items={rows.filter(f)}` | `const items = useMemo(() => rows.filter(f), [rows, f])` |
| `options={{}}` като default | константа извън компонента: `const EMPTY = {}` |
| `<Child><b/></Child>` | подай children отвън или ги направи prop на по-горно ниво |

Кога си заслужава да правиш това, е отделен въпрос: [useMemo и useCallback](useMemo_useCallback.md).

## Custom сравнение

`memo` приема втори аргумент, функция `(prevProps, nextProps) => boolean`. Връща `true`, ако рендерът трябва да се прескочи:

```jsx
const Row = memo(function Row({ item, onSelect }) { ... },
  (prev, next) => prev.item.id === next.item.id && prev.item.version === next.item.version,
);
```

Рисковете са реални. Ако сравнението пропусне prop, който влияе на изхода (тук `onSelect`), компонентът ще показва стари данни и ще вика стар callback с остарели затваряния. Deep сравнение на големи обекти може да е по-скъпо от самия рендер. Правило: custom compare само когато измерването показва, че трябва, и само върху полета, които наистина определят изхода.

## Кога memo помага и кога не

Помага, когато и двете са верни: рендерът на компонента е скъп (много елементи, тежко изчисление, голямо поддърво) и родителят се рендерира често със същите props за това дете. Типични примери: ред в голяма таблица при писане във филтър отгоре, графика до формуляр, списък до брояч.

Не помага, когато props почти винаги са нови (данни, които се сменят при всеки рендер), когато компонентът е евтин (сравнението на props струва почти колкото рендера) или когато родителят рядко се рендерира. В тези случаи memo добавя едно сравнение на всеки рендер и нула спестявания.

## React Compiler

От React 19 насам React Compiler (по-рано React Forget) автоматично мемоизира компоненти и стойности при build време: анализира кода и вмъква еквивалента на `memo`, `useMemo` и `useCallback` там, където е безопасно. Идеята е точно тази страница да стане ненужна за ръчно прилагане. Докато не ползваш компилатора, правилата по-горе важат с пълна сила, а и с него е полезно да разбираш какво прави за теб.

## Капани

- `memo` не е deep compare. Промяна вътре в обект (мутация) не се забелязва: `item.name = 'x'` без нова референция оставя детето със стария изглед.
- `memo` не спира рендер от собствен `setState` или от `useContext`, чиято стойност се смени. Спира само рендера "защото родителят се рендерира".
- Мемоизиран компонент с inline children е самозалъгване: изглежда оптимизиран, а се рендерира всеки път.
- Не увивай всичко. Сравнението не е безплатно, а кодът става по-труден за четене.
