# useMemo и useCallback: реалната цена

`useMemo` запомня резултат от изчисление, `useCallback` запомня функция. И двата връщат старата стойност, ако зависимостите не са се променили. Полезни са точно в два случая: когато изчислението е наистина скъпо и когато ти трябва стабилна референция за `React.memo` дете или за dependency на ефект. Във всички останали случаи те са излишна преоптимизация с реална, макар и малка, цена.

## Аналогия: бележник до печката

Готвач, който всеки път претегля едни и същи 200 грама брашно, може да си запише резултата в бележник и да не тегли повече. Но ако записва всяко нещо, което прави, ще прекарва повече време в писане и търсене из бележника, отколкото в готвене. Бележникът (useMemo) има смисъл за дълги изчисления с еднакъв вход, не за "две плюс две".

## Какво точно пази useMemo

Всеки hook живее в свързания списък на fiber-а (виж [Свързан списък](Linked_List.md)). За `useMemo` hook обектът пази двойка `[стойност, deps]`:

```js
// Опростено от React
function updateMemo(create, deps) {
  const hook = updateWorkInProgressHook();
  const prev = hook.memoizedState;              // [value, deps] от миналия рендер
  if (prev !== null && areHookInputsEqual(deps, prev[1])) {
    return prev[0];                              // deps съвпадат: върни старото
  }
  const value = create();                        // иначе изчисли наново
  hook.memoizedState = [value, deps];
  return value;
}

function areHookInputsEqual(next, prev) {
  for (let i = 0; i < prev.length; i++) {
    if (!Object.is(next[i], prev[i])) return false;
  }
  return true;
}
```

`useCallback(fn, deps)` е буквално `useMemo(() => fn, deps)`: запомня самата функция вместо резултата ѝ.

## Реалната цена

- Памет: старата стойност и старият deps масив живеят в fiber-а, докато компонентът е монтиран, дори да не трябват повече. При хиляди компоненти това се трупа.
- Процесор: при всеки рендер React обхожда deps и ги сравнява с `Object.is`. При всеки рендер се създава и нов deps масив, и нова `create` функция, независимо дали кешът ще улучи.
- Четимост: всяка стойност, увита в hook, е още един ред, още един deps масив, още едно място за грешка (пропуснат dep = стара стойност).

Цената на единичен `useMemo` е микросекунди. Проблемът не е, че е скъп, а че често не носи нищо. Демото по-долу го измерва на твоята машина.

## Демо: цената на мемоизацията на тривиални стойности

Резултатът обикновено е няколко процента в полза на версията без hooks. Не е драматично, но е в грешната посока: платен е код и памет за нулева полза. Когато изчислението струва милисекунди, същият `useMemo` спестява хиляди пъти повече, отколкото струва.

## Кога са полезни

| Ситуация | Трябва ли | Защо |
|---|---|---|
| Обект или масив, подаван на `memo` компонент | да, `useMemo` | иначе memo никога не улучва |
| Функция, подавана на `memo` компонент | да, `useCallback` | същата причина |
| Стойност в deps на `useEffect`, която е обект | да | иначе ефектът се пуска всеки рендер |
| Сортиране или филтриране на хиляди елементи | да, ако е измерено | спестява милисекунди при всеки рендер |
| `price * qty` | не | примитив, евтино |
| Функция, подавана на обикновен `<button onClick>` | не | DOM елементите не сравняват props |
| Функция, подавана на дете без memo | не | детето се рендерира така или иначе |
| Компонент, който се рендерира веднъж на минута | не | няма какво да се спестява |
| Стойност, чиито deps се менят всеки рендер | не | кешът никога не улучва |

Пример за правилно приложение, с бележка за измерването:

```jsx
function Report({ rows, query }) {
  // измерено с Profiler: 6 ms при 10 000 реда, query се сменя на всяка буква, rows веднъж на зареждане
  const filtered = useMemo(() => rows.filter((r) => r.name.includes(query)), [rows, query]);
  const onExport = useCallback(() => exportCsv(filtered), [filtered]);
  return <Table rows={filtered} onExport={onExport} />;   // Table е memo()
}
```

## Типични грешки

- `useMemo(() => x, [])` с празни deps, докато `x` се променя: връща вечно старата стойност. ESLint правилото `react-hooks/exhaustive-deps` хваща това.
- Мемоизиране "за всеки случай" на всеки ред в компонента. Кодът става два пъти по-дълъг, а полза няма.
- `useCallback` върху функция, която се подава само на DOM елемент или на дете без `memo`. Референцията е стабилна, но никой не я сравнява.
- Очакване, че `useMemo` е гаранция. React документацията изрично казва, че може да "забрави" кеширани стойности (например при бъдещи оптимизации на паметта). Кодът трябва да е коректен и без кеша.
- Поставяне на страничен ефект в `useMemo`. Той се изпълнява по време на render, който трябва да е чист (виж [Какво е Fiber](Fiber.md)).

## React Compiler

React Compiler прави това автоматично: при build анализира всеки компонент и мемоизира стойности и JSX там, където правилата на React гарантират, че е безопасно. С него ръчните `useMemo` и `useCallback` стават почти ненужни, а грешките с deps изчезват, защото компилаторът ги изчислява. Докато не го ползваш (или ако кодът ти нарушава правилата и компилаторът го прескача), решавачът по-горе е пътят.

## Капани

- Deps се сравняват с `Object.is`, значи обект в deps трябва сам да е стабилен, иначе си преместил проблема едно ниво нагоре.
- `useMemo` за JSX (`useMemo(() => <Big/>, [])`) работи, но е по-четливо да извлечеш `Big` в `memo` компонент.
- Мемоизацията не прави нищо по-бързо първия път. Помага само от втория рендер нататък.
